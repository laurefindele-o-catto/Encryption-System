# Backend Technical Summary

This repository implements a working DRPE-based image encryption system built around image-derived key material. The active contract is now clear and consistent: the sender and receiver provide a key image and a second secret image used to derive the password material before DRPE key generation.

## 1. System architecture

The stack is deliberately small and modular:

- FastAPI in `backend/` exposes the encrypt and decrypt endpoints
- `backend/services/drpe.py` performs the actual Fourier-domain DRPE math
- `backend/services/keys.py` derives the phase masks from cryptographic key material
- `backend/controllers/image_controller.py` orchestrates the request lifecycle
- `backend/routers/image_router.py` exposes the HTTP contract
- `frontend/src/pages/AlicePage.jsx` and `frontend/src/pages/BobPage.jsx` provide the role-based UI

The core data flow is:

1. Alice uploads a cover image
2. Alice uploads a secret key image
3. Alice uploads a password image
4. The frontend hashes the password image and sends the digest as `secret_password`
5. The backend derives a password key and mixes it with the key image digest to build P1/P2 materials
6. The DRPE encryption returns a ciphertext payload and a visual preview
7. Bob uploads the same key-image pattern and matching password image to decrypt

---

## 2. Actual key model

The important change is that the system does not rely on a human-typed password string. Instead, the password is image-derived material.

The actual backend behavior is:

- `secret_key_image` is read and canonicalized
- the key image is hashed into a deterministic digest
- `secret_password` is passed in as a text string derived from a second image, usually a SHA-256 hex digest
- `derive_image_password_keys(...)` combines the password-derived key, the image digest, the `message_id`, the `salt`, and `frame_index`
- those values generate the two masks used by DRPE: `p1_material` and `p2_material`

This is the real model reflected in `backend/services/keys.py` and `backend/controllers/image_controller.py`.

## 3. Active backend endpoints

### `POST /api/encrypt`

Form fields:

- `cover_image`: uploaded image file
- `secret_key_image`: uploaded key image
- `secret_password`: string value produced from a second image digest, not a typed password
- `message_id` (optional)
- `frame_index` (optional, usually `0`)

Returns:

- `ciphertext_b64`
- `ciphertext_shape`
- `image`
- `energy`
- `cover_energy`
- `message_id`
- `salt_b64`

### `POST /api/decrypt-with-key-images`

Form fields:

- `ciphertext_b64`
- `ciphertext_shape`
- `secret_key_image`
- `secret_password`
- `message_id`
- `salt_b64`
- `frame_index`

Returns:

- `image`
- `energy`
- `match_with_cover`

### `GET /api/health`

Returns `{"status": "ok"}`

## 4. DRPE math

The implementation in `backend/services/drpe.py` follows the standard 4-f DRPE structure:

- multiply the cover image by `exp(j * P1)` in the spatial domain
- apply FFT2
- multiply by `exp(j * P2)` in the Fourier domain
- apply IFFT2 to produce the complex ciphertext
- recover by undoing the same P2 and P1 operations during decryption

The output used for display is the magnitude image `|ciphertext|`.

---

## 5. Important design notes

- The backend does not treat a free-form password as the primary security secret.
- The real seed material is derived from the image-based key material and the password image digest.
- `message_id` and `salt` are used to avoid deterministic reuse across messages.
- A matching receiver must use the same key-image material and the same password-image-derived secret to recover the original cover image.
- The system is intentionally phase 1 only. Morse or channel layering is not part of the current backend functionality.

---

## 6. Why the old docs were wrong

The earlier project files described a simplified DRPE demo with a free-text password and an outdated phase-2 framing. That is not the actual live behavior of this codebase.

The authoritative architecture now is:

- image-derived key material
- key image + derived password image
- DRPE masks generated by `derive_image_password_keys(...)`
- encrypted packet and decrypt flow as implemented in the current backend routes

The repository should therefore be read with the current backend contract and the current frontend workflow as the ground truth.
